The problem

Recurring decisions need speed and a confidence you can act on

“Which team owns this ticket?” A fixed option set, asked thousands of times.

What the decision needs

  • An answer in milliseconds
  • A probability you can threshold on
  • No dropped or doubled events

What a plain LLM call gives

  • Slow: it generates text token by token
  • Uncalibrated: “I'm 95% sure” means little
Architecture

You bring the topic and the config. It handles the rest.

1 · You set up

An ingestion topic and one config file. That is all.

2 · It routes

One command starts deciders, model serving, per-option streams and dead-letter.

3 · You watch

A live dashboard shows each decision, confidence and tier as it happens.

Tier 1

Decide in one forward pass

  • Qwen3-8B (Q8_0) reads the prompt
  • Take the logits of the option letters at the answer position
  • Softmax, divided by a temperature, gives probabilities
  • No text generated
~50 ms

per decision

Swappable model

The model is configuration. Pick a smaller one for latency or a larger one for accuracy, then refit the temperature.

Serving engineering

Measure, then fix

Latency

  • Prefill is 98% of latency
  • The Python path added 110 ms
  • A last-logit read removed it

Concurrency

  • Flask dev server crashed at 4 concurrent requests (llama.cpp context is not thread-safe)
  • Single-worker waitress + model lock: 16 concurrent, 0 errors
Pipeline reliability

Never lose, never double

  • Consumer groups
  • Retries with backoff
  • XAUTOCLAIM reclaims abandoned messages
  • One Lua script forwards, acknowledges and de-duplicates atomically
  • Config validation rejects a reclaim time shorter than the HTTP timeout, which would decide slow events twice
